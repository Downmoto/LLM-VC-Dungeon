== Project Evolution

The project was developed over four milestones, each producing a written report. Taken together, they trace a path from an ambitious voice-first concept through two major architectural pivots to a stable, tested, containerized deliverable. This section summarizes each milestone and explains the decisions that shaped the final design.

=== Milestone 1: Project Refinement and Technical Strategy

The first milestone established the project charter. The core problem, syntax friction in text adventure games, was defined clearly, and the proposed solution was a "Voice First" web application in which players speak naturally and receive synthesized audio narration from an AI dungeon master.

A dual-stack architecture was designed to support both commercial and self-hosted deployment. The commercial stack targeted Groq for speech-to-text and narrative generation, a local Function Gemma model for structured intent logic, and Lemonfox for text-to-speech. The self-hosted stack substituted Faster-Whisper, a local Llama 3 model, and Piper TTS, enabling fully offline operation for research or privacy-sensitive contexts.

A financial model projected variable API cost at approximately $0.00063 USD per game turn, establishing that the system was commercially viable at scale. A rate limiter and per-session turn limit were identified as necessary safeguards against budget overruns.

The milestone also defined a data strategy for evaluating intent classification: a synthetic dataset of 200 to 300 natural language command / expected function-call pairs, generated by a stronger model such as GPT-4 and used to benchmark prompt engineering accuracy. This evaluation dataset was ultimately not built during the project; the intent classification validation was handled instead through the backend test suite introduced in Milestone 3.

The team was divided into three specializations: frontend, AI engineering, and integration, and a WebSocket architecture was specified for persistent player connections to avoid serverless timeout constraints.

=== Milestone 2: Core Gameplay Loop and Hybrid Architecture

The second milestone introduced the features that define the game's interface. The most significant was the hybrid command system: a distinction between system-level slash commands, such as `/save`, `/load`, `/theme`, and `/help`, which are handled deterministically by the frontend without any API call, and narrative natural language inputs, which are forwarded to the backend for LLM processing.

The generation strategy was also restructured. Rather than relying on the LLM to construct dungeon content from scratch on every turn, a procedural Python layer was introduced to generate room topology as a connected graph. The LLM's role was narrowed to adding narrative flavor on top of that deterministic structure. This separation proved to be the conceptual foundation for the more complete migration that followed in Milestone 3.

On the frontend, Svelte 5 rune-based reactive stores were adopted for invisible state tracking. On the backend, Ollama was selected as the primary local inference runtime during development, providing cost-free, private model access with easy provider switching. The game state response contract was expanded to include player and room snapshots alongside the narrative reply.

Voice output via TTS was prototyped but integration complexity and latency constraints foreshadowed its eventual de-scoping.

=== Milestone 3: Programmatic Core Migration

The third milestone was the most architecturally significant. Previous iterations had validated the LLM-driven gameplay concept, but intent classification and room expansion were still tightly coupled to model responses. The latency of round-tripping every player input through an LLM, combined with the inconsistency of structured JSON output from smaller models, made the system unreliable as a game foundation.

The response was a full migration of core gameplay to deterministic Python. Three key systems were rebuilt without LLM dependency:

A runtime mode flag, `GAME_MODE`, was introduced with three values: `programmatic` for fully deterministic operation, `hybrid` for parser-first with LLM fallback, and `llm` for strict LLM-only classification. A companion flag, `ENABLE_LLM_NARRATION`, decoupled narrative enrichment from gameplay correctness. This allowed the game to run correctly at zero LLM cost while preserving the option for richer output when a provider was available.

A dedicated intent parser replaced the LLM classifier for common actions. The parser handles movement with direction aliases, item and enemy targeting via token-overlap scoring, and conversational input normalization. It returns a structured intent object identical in schema to the LLM classifier's output, enabling transparent interoperability.

Procedural generation was expanded from simple random content to structured biome tables. Each dungeon theme maps to a biome: mine, crypt, arcane, or volcanic; and each biome carries tables of themed descriptors, features, items, and enemies. Room difficulty scales by position in the dungeon, governing item and enemy spawn rates and enemy HP bands.

A backend test suite was introduced covering intent parsing, game turn behavior, and generation correctness.

=== Milestone 4: Merge Integration and Runtime Hardening

The fourth milestone consolidated everything into a deployable, production-grade baseline. The scope was driven by the integration of a large pull request encompassing 28 changed files, touching backend, frontend, tests, and deployment.

Containerization was completed: `Dockerfile.backend`, `Dockerfile.frontend`, and `docker-compose.yml` define the full deployment stack, with explicit health checks and an optional Ollama Compose profile for local model workflows. Environment configuration was standardized via `.env.example`.

API behavior was hardened in several areas. The save and load paths now enforce directory boundary checks, preventing path traversal attacks by sandboxing all file operations within the `data/` directory. New endpoints were added for game loading (`POST /api/load-game`) and map retrieval (`GET /api/game/map`). The turn response was expanded to include the current room ID, player HP and maximum HP, inventory size, and history size, giving the frontend reliable state context for diagnostics and rendering.

The game logic itself matured: a deterministic `health` action was added, combat now includes enemy retaliation and explicit game-over signaling when player HP reaches zero, visited rooms return distinct messaging, and the `query` action stores extracted facts on entities for persistence across turns.

The test suite grew from its Milestone 3 introduction to 43 total backend tests. The frontend gained `/load-game` and `/map` commands, with the map command rendering an ASCII grid of discovered rooms.
